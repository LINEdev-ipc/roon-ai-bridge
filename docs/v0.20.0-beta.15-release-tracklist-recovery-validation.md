# v0.20.0 Beta 15 Release Tracklist Recovery Validation

## Why this beta exists

Beta 14 restored exact-version precision and reached 934/1,000 requested
positions in the complete deployed validation. The remaining 66 positions were
concentrated in remixes, live recordings and acoustic/cover selections:

| Case | Beta 14 | Main remaining rejection |
| --- | ---: | --- |
| P06 remixes | 68/100 | MusicBrainz not found and Roon binding |
| P07 live | 75/100 | Roon binding and MusicBrainz ambiguity |
| P08 acoustic/covers | 91/100 | Roon binding |

The warm P06 run showed that MusicBrainz caching was already effective, while
Roon still performed 213 searches for 100 requested positions.

A real ChatGPT request exposed the same recovery problem in an ordinary
single-artist playlist. `The Rolling Stones — Esenciales` requested 30 songs,
supplied 38 candidates and finished its first call in 60.0 seconds with only 5
accepted and 33 rejected. ChatGPT then used the edit tool and added eight more,
leaving a 13/30 playlist. The stored tracks also showed that sparse Roon
results can omit their album and that a bounded MusicBrainz recording payload
can expose a later compilation or reissue instead of the requested album.

## Corrective design

The existing direct search remains the fast path. Beta 15 adds recovery only
after that path fails.

### MusicBrainz release-tracklist recovery

- A failed title/artist lookup with a known album performs one bounded
  recording-index query for the album and recording artist.
- Returned recordings must still pass title, artist, requested release and
  version-family validation.
- Release-group primary and secondary types are version evidence, so a track
  on an album classified as `Remix` or `Live` does not need those words in its
  visible title.
- Results are cached by normalized album and artist, deduplicated while a
  request is in flight and persisted for future playlist builds.
- The recording-resolution cache namespace is `v10`; stale Beta 14
  not-found decisions cannot suppress the new recovery.

This follows the MusicBrainz model: a recording is the canonical audio
identity, while a release track proves that the recording occurs on the
requested release.

### Roon verified-album recovery

- Exact-version candidates try a Roon album tracklist after direct binding
  fails and before the old flat title/artist/album fallback.
- Standard candidates retain the old fallback order and use album navigation
  only after all existing track searches fail.
- Only ordered, identity-verified album details are accepted.
- The matched track must still pass title, required credits and version gates.
- Multiple same-title tracks remain unresolved unless ISRC, canonical duration
  or an equivalent observed recording key makes them the same recording.
- Album searches and album-detail reads are shared across all candidates in a
  build. The verified detail is also handed to metadata enrichment, preventing
  a second album read for every accepted track.
- Build performance reports count MusicBrainz recoveries, Roon recoveries and
  reused Roon album operations; per-candidate diagnostics expose the same
  evidence.

Roon remains the playback provider. Album membership is evidence for choosing
the playable item; it never replaces MusicBrainz as canonical identity.

### Metadata coherence and MCP guidance

- If an observed album has no compatible MusicBrainz release-group candidate,
  the profile leaves the release group empty instead of substituting an
  unrelated compilation or later reissue.
- MCP instructions now require every known `album_hint`, including standard
  songs, because it enables safe release-tracklist recovery.
- The model is told to set `no_adjacent_same_artist=false` for one-artist
  playlists or any intentionally repetitive selection.
- Creation, editing and reconstruction continue to use the same production
  services; no parallel legacy or test-only resolver was added.

## Automated regressions

Focused tests cover:

- two Rolling Stones songs recovered from one cached MusicBrainz album query;
- `Eleanor Rigby / Julia (transition)` recovered from the `Love` release group
  classified as a remix;
- two Rolling Stones songs recovered from one Roon album search and one album
  detail read;
- refusal to expose `Kid A / Amnesiac` as the canonical release group when the
  requested album was `Kid A`;
- the existing exact-live, cover, acoustic, canonical-duration and wrong
  Nina Simone performance gates.

## Required validation before deployment

1. Run the complete automated test suite and TypeScript build.
2. Regenerate and audit the 1,505-candidate fixture set.
3. Exercise the Rolling Stones regression through the real playlist MCP
   contract with diagnostics enabled.
4. After deployment, rerun P06-P08 first and audit accepted identities.
5. If precision remains intact, rerun P01-P10 to confirm that the standard fast
   path still reaches its previous results.

## Local validation

Local release preparation completed successfully:

- complete automated suite: 315 passed, 0 failed;
- focused playlist/catalog/recording suite: 57 passed, 0 failed;
- TypeScript production build: passed;
- fixture regeneration: passed for 10 playlists and 1,505 candidates;

  timestamp changed and was not retained.

Live P06-P08 and complete P01-P10 measurements remain deployment validation,
not local release evidence. The existing Rolling Stones playlist was inspected
