# v0.20.0 Beta 9 Integrated Playlist Validation

## Scope

Beta 9 replaces model-driven search and replenishment loops with a one-call
playlist build pipeline:

- explicit permanent versus temporary playlist intent;
- adaptive primary and reserve pools;
- MusicBrainz word-based recording search;
- concurrent ListenBrainz ACR/ACRR advisory lookup;
- speculative Roon discovery in parallel with catalog resolution;
- canonical reranking, fallback and persisted Roon binding;
- verified partial completion and end-to-end performance telemetry.

## MCP contract

- Any request that asks to create, make, prepare, build, generate or curate a
  playlist/list is permanent and uses `roon_save_playlist`.
- A temporary playlist is only a hidden helper for immediate playback commands
  such as "play music" or "pon musica" when no playlist artifact was requested.
- The model calls playlist creation once and does not call
  `roon_search_media` first.
- Candidate pools contain 125% for standard requests, 140% for constrained
  requests and 160% for exact versions or performance-sensitive requests.
- RoonIA consumes reserves internally and saves a verified partial playlist
  when the target cannot be reached.
- The removed `build_id` replenishment contract has no compatibility alias.

## Provider responsibilities

- MusicBrainz is the canonical recording and metadata authority.
- ListenBrainz supplies candidate MBIDs and agreement signals but never decides
  identity.
- Roon supplies the playable catalog observation and binding.
- A speculative Roon result is accepted only after reranking it against the
  canonical MusicBrainz title, credits and recording family.

## Automated validation

The complete local suite and build must pass:

```powershell
pnpm run test
pnpm run build
```

Result on 2026-07-28:

- 286 tests passed, 0 failed;
- TypeScript build passed;
- fixture audit passed for 10 playlists and 1,430 candidates, with no duplicate
  audit identifiers or leaked MusicBrainz recording IDs.

Coverage includes one-shot partial completion, reserve stopping and reporting,
temporary intent, MCP schemas and instructions, broad MusicBrainz word search,
soft album evidence, concurrent ListenBrainz datasets, speculative Roon
discovery, canonical fallback and binding persistence.

## Exhaustive pre-deployment validation

`validation/playlist-e2e-beta9` contains ten ordinary human prompts, each
requesting 100 tracks. The generated pools contain 1,430 candidates in total
and omit MusicBrainz IDs, forcing the production resolver to rediscover
identity and complete Roon binding.

The runner uses the isolated **RoonIA Beta 9 Validation** extension and a
validation-only SQLite database. Results are incremental and record:

- requested, added and missing tracks;
- every rejection grouped by reason;
- candidates started and reserves left unused;
- MusicBrainz, ListenBrainz, Roon and hydration timing;
- provider request and cache-hit counts for MusicBrainz and ListenBrainz;
- exact Roon search counts;
- speculative bindings reused and canonical fallbacks;
- persisted binding count and total wall-clock time.

## Real P01 result

The first deployed pilot completed on 2026-07-28 and failed the gate:

- 67 of 100 requested tracks saved;
- 33 missing;
- 625,701 ms wall-clock time;
- 272 MusicBrainz requests, 207 ListenBrainz requests and 179 Roon searches;
- 19 MusicBrainz provider failures, 20 identities not found, 17 unresolved
  Roon bindings and 2 duplicates.

The remaining nine playlists were intentionally not run. Beta 9 is not an
acceptable playlist baseline; its corrective implementation and next gate are
documented in the Beta 10 validation report.
